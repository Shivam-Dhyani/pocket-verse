# 2026-10-19

## Upload speed: reuse a warm storage connection per account

- **Report:** a folder of 3 images (3.4 MB total) took 30+ s to upload on the
  live deployment (web on Vercel, API on Render free, DB on Neon).
- **Root cause (code):** every chunk upload opened a brand-new Telegram
  connection and destroyed it afterwards. Inside GramJS that's: TCP + MTProto
  init with a config fetch on the main connection, then — because
  `uploadFile` calls `getSender(dcId)` → `_borrowExportedSender` — a **second**
  connection just for file parts, preceded by **another** config fetch (a fresh
  client has nothing cached). Only then the parts and the message post. The
  per-user lock (ADR-0003) runs an account's transfers one at a time, so a
  folder paid that setup once per file, back to back, from Render's default
  Oregon region to a distant Telegram data centre.
- **Ruled out:** CPU — GramJS encrypts with pure-JS AES-IGE, but a local
  benchmark puts 3.4 MB at ~70 ms on one core (≈0.7 s at Render free's 0.1 CPU);
  the queue (in-process jobs start immediately; BullMQ concurrency 2); rate
  limits (uploads allow 10,000 req / 15 min); the browser (3 files in parallel,
  2.5 s polling).
- **Fix:**
  - `lib/telegram/gramjs.ts`: a warm-connection pool, one per session (keyed by
    a SHA-256 of the session). `uploadFile` and `deleteMessages` acquire and
    release it; it closes after 60 s idle (`unref`'d timer). A connection that
    fails an operation or dropped while idle is retired so the retry reconnects
    cleanly; `logOut` retires the session's warm connection. New `prewarm()` and
    `close()` on the gateway.
  - `modules/files/files.service.ts` `createUpload`: calls `gateway.prewarm()`
    so the connection opens while the browser is still sending bytes.
  - `index.ts`: graceful shutdown closes warm connections.
  - `storage.worker.ts`: the "started" log now fires once the per-user lock is
    held, with `waitedMs`; "finished" logs `transferMs` (ms, not rounded
    seconds) and `reusedConnection`.
  - Per-account serialization is unchanged — FLOOD_WAIT protection stays.
- **Not fixable in code (documented):** cold starts on Render free (~30–60 s
  after 15 min idle — if the slow upload was the first action after a quiet
  spell, that alone explains it) and distance: `render.yaml` sets no region, so
  the API runs in Oregon. New "Upload speed" section in `docs/DEPLOYMENT.md`
  (co-locate Render + Neon near users, e.g. Singapore for South / South-East
  Asia; how to read the new timing logs) and a region comment in `render.yaml`.
- **Areas:** `apps/api/src/lib/telegram/{gateway,gramjs}.ts`, new
  `gramjs.test.ts`, `test-utils/fake-gateway.ts`, `modules/files/{files.service,
storage.worker}.ts`, `modules/files/files.test.ts`, `index.ts`; docs:
  ADR-0014 (+ index, cross-link from ADR-0003), `docs/DEPLOYMENT.md`,
  `docs/DATABASE.md` (upload flow step 1), `docs/DEVELOPMENT_JOURNEY.md`,
  `render.yaml`.
- **Verification:** 8 new pool tests against a mocked GramJS client (one connect
  for consecutive uploads, separate accounts separate, prewarm reused, failed
  transfer → fresh connection, dead idle socket → reconnect, 60 s idle close,
  deletes share the connection, log-out retires it) — all 8 **fail** against the
  previous adapter and pass now. New files test asserts `createUpload` prewarms
  before any upload. 156 API tests, typecheck, lint, web build pass. Not
  verifiable here: real timings against Telegram (sandbox egress blocks Render,
  Vercel and Telegram) — the new `transferMs` / `reusedConnection` log fields
  are how to confirm in production.
- **Follow-ups:** if large folders still feel slow after the hosting fixes,
  consider a small bounded per-account transfer parallelism (would revise
  ADR-0003).

## Drop the "stored" chip; folders show "syncing N files" while their contents upload

- **What:**
  - A stored file no longer shows a **"stored"** chip — every file ends up
    stored, so it carried no information. Only states that need attention keep
    a badge: `syncing N%`, `upload failed`, `unavailable`.
  - A folder with files still uploading/syncing **anywhere inside it** (any
    depth) shows a **"syncing N files"** chip — in list and grid views — and stays
    fully openable. The chip clears by itself once everything inside has landed.
- **Why:** user request — "stored" was noise; a folder mid-upload should say so
  without blocking access to it.
- **How:**
  - API `folders.service.listDrive` adds `syncingCount` to each listed folder via
    `syncingCountsFor()`: one query for the account's `UPLOADING` files; only if
    any are nested in folders, one query for the folder tree, walked upwards in
    memory (listed folders are siblings, so a file counts toward at most one).
    `ERROR` and `LOST` files aren't in progress and don't count.
  - Shared `folderDtoSchema` gains optional `syncingCount` (present in drive
    listings).
  - Web: `StatusBadge` renders nothing for `ready`; new `FolderSyncBadge` (same
    look as the file "syncing" badge, with a tooltip). The drive query keeps
    polling while any listed folder is syncing — otherwise the parent view
    stopped polling once the browser finished sending bytes, and the chip would
    have stuck until a refresh. Removed the now-unused `.pv-badge--ok` style and
    `CheckIcon` import.
- **Areas:** `apps/api/src/modules/folders/folders.service.ts` (+ test),
  `packages/shared/src/schemas/files.ts`, `apps/web/src/components/{ui,drive-views}.tsx`,
  `apps/web/src/app/drive/page.tsx`, `apps/web/src/app/globals.css`,
  `docs/DATABASE.md`.
- **Verification:** new folders test — two files mid-upload two levels deep
  count toward the top folder (and the nested one when inside it), a finished
  and a failed file elsewhere don't, and the count drops as files land. 157 API
  tests, typecheck, lint, web build pass. Headless browser on a mocked API: list
  and grid show "syncing 3 files" on the busy folder, nothing on the finished
  one, no badge on a stored file, "syncing 60%" kept on a syncing file; the chip
  cleared on its own after the 4th poll; the syncing folder opened normally.
