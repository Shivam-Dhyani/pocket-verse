# 2026-09-30

## Distinct "lost" file state + clean download pre-flight (deleted-in-storage handling)

Handling for files that uploaded fine, then had their data deleted **inside the
user's storage** (by hand). Previously these were collapsed into the `ERROR`
(upload-failed) state, mislabelled "upload failed", and only detected when a
download broke mid-stream — handing the browser a corrupt partial file, and on a
second attempt an inaccurate error (`"This file failed to upload…"`). Implemented
A1 + B1 + C1 + C3 from the options discussion.

- **What (A1 — distinct state):** New `LOST` file status end-to-end, separate from
  `ERROR`. Uploaded-then-deleted files are marked `LOST`; the badge reads
  **"unavailable"** (dashed, distinct from "upload failed"), and the download
  error is honest: `410 FILE_UNAVAILABLE` — _"This file was deleted from your
  storage, so it can no longer be downloaded."_
- **What (B1 — pre-flight):** `download()` now verifies every chunk message still
  exists **before any response headers are committed** (one batched lookup over
  the same download connection). A missing chunk → mark `LOST` + log + clean 410,
  never a corrupt partial download. `download-token` does a cheap DB-only
  readiness gate (`getDownloadableFile`) so an already-known-bad file is refused
  in-app before the download navigation. The mid-stream failure path remains as a
  backstop (marks `LOST` for a chunk deleted in the tiny window after pre-flight).
- **What (C1 — remove affordance):** For a `LOST` file the row action and confirm
  dialog read **"Remove from Pocketverse"** (not "Delete") and explain the bytes
  are already gone — the removal only clears the leftover listing entry.
- **What (C3 — explain in context):** The "unavailable" badge is a link to
  `/activity` (where the loss is already recorded via the `file.unreachable`
  audit event) with a tooltip explaining what happened.
- **Root cause of the original report:** the reported `FILE_NOT_READY` /
  "failed to upload" error was the `ERROR`-status message being reused for a
  deleted-after-upload file; detection only happened on a (corrupting) download
  attempt, which flipped the file to `ERROR`.
- **Areas:**
  - API: `prisma/schema.prisma` (+`LOST` enum) and migration
    `20260930120000_file_lost_status`; `lib/telegram/gateway.ts` +
    `gramjs.ts` (new `Downloader.verifyPresent`); `test-utils/fake-gateway.ts`;
    `modules/files/files.service.ts` (`download` pre-flight, `getDownloadableFile`,
    `markFileLost`/`fileLostError`/`notDownloadable`, `recordDownloadFailure` now
    marks `LOST`, status maps); `modules/files/files.routes.ts` (download-token
    gate).
  - Shared: `schemas/files.ts` (`fileStatusValues` +`'lost'`).
  - Web: `components/ui.tsx` (`StatusBadge` lost → linked "unavailable"),
    `globals.css` (`.pv-badge--lost`), `components/drive-views.tsx` +
    `app/drive/page.tsx` (Remove label + dialog copy).
  - Docs: `docs/DATABASE.md` (status values, download flow, download-token).
- **Verification:** updated the "marks a file lost" API test to assert a clean
  `410 FILE_UNAVAILABLE` (no corrupt stream), `status: 'lost'`, the audit event,
  and an in-app 410 from `download-token`. `pnpm typecheck && lint`, 144 API tests,
  web build all pass. Headless-browser check: "unavailable" badge links to
  `/activity` with tooltip; lost row shows **Remove** (no Download); the confirm
  dialog reads "Remove from Pocketverse".
- **Follow-ups (not in scope here):**
  - **Zip / multi-select download** does not yet pre-flight per file — a freshly
    deleted file inside a zip selection can still break the zip mid-stream, and
    that path's `onError` passes `null` so it isn't marked `LOST`. Worth
    extending `prepareZip` to verify + skip/mark lost.
  - **Proactive detection (option B2)** was deferred: losses are still only found
    when a download is attempted. A periodic reconciliation sweep would make the
    drive trustworthy before anyone clicks (needs FLOOD_WAIT-aware batching).

## Self-heal: a fully-stored file stuck in ERROR is reclassified, not shown "upload failed"

Follow-up to the LOST work above, from a user report: a file they'd deleted in
Telegram was still showing **"upload failed"** (`ERROR`) rather than
"unavailable" (`LOST`).

- **Root cause:** `ERROR` had two meanings collapsed together. A genuine upload
  failure never reaches storage (its chunk has no `telegramMessageId`). But a
  file that WAS fully stored (reached `READY`), then had its data deleted, could
  also be sitting in `ERROR` — because the pre-fix download code marked missing
  data as `ERROR`, and those files can never self-correct: the download path
  short-circuited on `status === 'ERROR'` and returned "This file failed to
  upload…", never re-checking storage.
- **Fix:** distinguish the two by whether the file was ever fully stored —
  `wasFullyStored(chunks)` = every chunk has a storage message id. `download()`
  and `getDownloadableFile()` now let an `ERROR`-but-fully-stored file through to
  the storage pre-flight instead of refusing it: data gone → reclassify `LOST`
  (honest 410 + "unavailable"); data still present → repair to `READY`. A genuine
  upload failure (not fully stored) still returns "upload failed" and offers
  retry.
- **Retry sync:** `retryFailed()` applies the same reclassification — a
  fully-stored `ERROR` file is verified and moved to `LOST`/`READY` rather than
  re-uploaded, so it leaves the "retry sync" banner. Return shape gains `lost`;
  the web shows a distinct "deleted from your storage → marked unavailable"
  notice instead of "needs a fresh upload".
- **Areas:** `apps/api` `modules/files/files.service.ts` (`wasFullyStored`,
  `download`/`getDownloadableFile` guards + READY repair, `retryFailed`
  reclassification), `test-utils/fake-prisma.ts` (FileRow `LOST`); `apps/web`
  `lib/files.ts` (+`lost`), `app/drive/page.tsx` (retry notice); `docs/DATABASE.md`.
- **Verification:** two new API tests — a fully-stored file forced to `ERROR`
  with its data gone returns `410 FILE_UNAVAILABLE` and becomes `lost` on
  download, and `retry-failed` reports `lost: 1` and reclassifies it. 146 API
  tests, typecheck, lint, web build all pass.
- **Note on the reported file:** a file that never _confirmed_ its upload (its
  chunk has no message id — e.g. the upload's confirmation was lost to a
  timeout) genuinely cannot be verified against storage, so it stays "upload
  failed" and offers retry (re-uploading from staged bytes is the real recovery).
  Only files we know reached storage can be proven lost.

## Exclude unavailable files from storage totals; unavailable files offer only "Remove"

From a user report: after a file is marked unavailable (LOST), the folder meta
still counted its bytes and it toward "1.4 MB · 2 files", and the row still
offered Rename/Move — pointless for a file whose data is gone.

- **Storage totals now mean available data.** `folders.service.subtreeSize` and
  the `/api/stats` aggregate exclude `LOST` files from both the byte total and
  the file count. `subtreeSize` additionally returns `unavailableCount`
  (`currentFolderSchema` gains it). So a folder of two deleted files reads
  "0 B available · 0 files · 2 unavailable" instead of "1.4 MB · 2 files", and
  the header storage chip no longer counts deleted-in-storage data as used.
- **Folder meta wording** (`app/drive/page.tsx`): when `unavailableCount > 0`,
  the size is qualified as "available" and a red "· N unavailable" is appended;
  otherwise unchanged.
- **Unavailable files offer only "Remove"** (`drive-views.tsx` `fileActions`):
  no Download (data's gone), no Rename/Move (pointless on a dead entry) — just
  the Remove affordance to clear the leftover listing entry.
- **Areas:** `apps/api` `modules/folders/folders.service.ts` (subtreeSize),
  `modules/activity/activity.routes.ts` (stats), `test-utils/fake-prisma.ts`
  (`matchesStatus`, `status: { not }` support in file count/aggregate);
  `packages/shared` `schemas/files.ts` (`unavailableCount`); `apps/web`
  `app/drive/page.tsx` (meta), `components/drive-views.tsx` (actions),
  `app/globals.css` (`.pv-folder-meta__unavailable`); `docs/DATABASE.md`.
- **Verification:** new folders test asserts a lost file is excluded from
  `totalBytes`/`fileCount` and counted in `unavailableCount`. 147 API tests,
  typecheck, lint, web build pass. Headless check: meta reads
  "… KB available · 1 file · 1 unavailable"; a LOST row shows only Remove while a
  READY row keeps Download/Rename/Move/Delete.
