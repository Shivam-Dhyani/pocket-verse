# 2026-09-30

## Distinct "lost" file state + clean download pre-flight (deleted-in-storage handling)

Handling for files that uploaded fine, then had their data deleted **inside the
user's storage** (by hand). Previously these were collapsed into the `ERROR`
(upload-failed) state, mislabelled "upload failed", and only detected when a
download broke mid-stream — handing the browser a corrupt partial file, and on a
second attempt an inaccurate error (`"This file failed to upload…"`). Implemented
A1 + B1 + C1 + C3 from the options discussion.

- **What (A1 — distinct state):** New `LOST` file status end-to-end, separate from
  `ERROR`. Uploaded-then-deleted files are marked `LOST`; the badge reads
  **"unavailable"** (dashed, distinct from "upload failed"), and the download
  error is honest: `410 FILE_UNAVAILABLE` — _"This file was deleted from your
  storage, so it can no longer be downloaded."_
- **What (B1 — pre-flight):** `download()` now verifies every chunk message still
  exists **before any response headers are committed** (one batched lookup over
  the same download connection). A missing chunk → mark `LOST` + log + clean 410,
  never a corrupt partial download. `download-token` does a cheap DB-only
  readiness gate (`getDownloadableFile`) so an already-known-bad file is refused
  in-app before the download navigation. The mid-stream failure path remains as a
  backstop (marks `LOST` for a chunk deleted in the tiny window after pre-flight).
- **What (C1 — remove affordance):** For a `LOST` file the row action and confirm
  dialog read **"Remove from Pocketverse"** (not "Delete") and explain the bytes
  are already gone — the removal only clears the leftover listing entry.
- **What (C3 — explain in context):** The "unavailable" badge is a link to
  `/activity` (where the loss is already recorded via the `file.unreachable`
  audit event) with a tooltip explaining what happened.
- **Root cause of the original report:** the reported `FILE_NOT_READY` /
  "failed to upload" error was the `ERROR`-status message being reused for a
  deleted-after-upload file; detection only happened on a (corrupting) download
  attempt, which flipped the file to `ERROR`.

- **Follow-ups (not in scope here):**
  - **Zip / multi-select download** does not yet pre-flight per file — a freshly
    deleted file inside a zip selection can still break the zip mid-stream, and
    that path's `onError` passes `null` so it isn't marked `LOST`. Worth
    extending `prepareZip` to verify + skip/mark lost.
  - **Proactive detection (option B2)** was deferred: losses are still only found
    when a download is attempted. A periodic reconciliation sweep would make the
    drive trustworthy before anyone clicks (needs FLOOD_WAIT-aware batching).
